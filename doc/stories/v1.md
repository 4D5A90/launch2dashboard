# launch2dashboard V1 — gestion locale de LaunchAgents

En tant qu'utilisateur macOS, je veux gérer mes services `launch2dashboard.*` depuis un dashboard local pour suivre leur état et diagnostiquer leurs logs sans écrire de commandes launchctl.

## Décisions
- Rust/Axum/Askama, assets incorporés au binaire, JS sans build.
- HTTP sur 127.0.0.1:9090 uniquement ; Host/Origin contrôlés et requêtes de mutation marquées pour bloquer les appels cross-site.
- Domaine pur (configuration, validation, états), port ServiceManager, adapter macOS isolant filesystem/launchctl, HTTP et UI en périphérie.
- Ajout de PUT /api/services/{id} pour l'édition et GET /api/services pour actualiser la liste.
- Ne pas interpréter des arguments via un shell. Une ligne par argument dans le formulaire.
- Stop décharge le job pour empêcher KeepAlive de le relancer ; Start recharge si nécessaire puis kickstart.
- Restart on failure utilise KeepAlive.SuccessfulExit=false, sans boucle après sortie réussie.
- Compteurs inconnus affichés « — », jamais inventés ; pas de CPU/RAM ni multi-host.

## Critères d'acceptation
```gherkin
Scenario: Liste limitée au namespace
  Given des plists gérés et non gérés
  When je charge le dashboard
  Then seuls les services launch2dashboard.* sont proposés
  And les erreurs de lecture sont visibles

Scenario: Création et modification
  Given une configuration valide avec chemins absolus et arguments explicites
  When je crée ou modifie un service
  Then un plist valide est écrit et chargé
  And une erreur launchctl est remontée sans annoncer un succès
  And une modification échouée restaure la configuration précédente autant que possible

Scenario: Arrêter un service qui redémarre automatiquement
  Given un service KeepAlive en cours
  When je demande Stop
  Then le job est déchargé et ne redémarre pas immédiatement

Scenario: Entrées invalides
  Given un id avec traversée de chemin ou une configuration invalide
  When je demande une mutation
  Then aucune commande ni écriture de service n'est exécutée

Scenario: Logs
  Given un service sélectionné
  When j'ouvre ses logs
  Then stdout et stderr sont identifiés et affichés comme texte
  And les nouvelles données arrivent via SSE sans croissance mémoire non bornée

Scenario: Navigateur
  Given le dashboard sur desktop ou mobile
  When je filtre, sélectionne, crée, modifie ou supprime un service
  Then les contrôles fonctionnent au clavier et les erreurs restent visibles
  And la suppression demande une confirmation explicite

Scenario: Origine HTTP étrangère
  Given une requête issue d'un autre site
  When elle tente une mutation
  Then le serveur la refuse
```

## Vérification
Tests domaine et adapter avec filesystem temporaire et commandes simulées ; tests route HTTP sans toucher aux services réels. cargo test, cargo check, cargo fmt --check, cargo clippy -- -D warnings. Inspection desktop/mobile de l'application ; aucun service réel démarré sans besoin explicite.
